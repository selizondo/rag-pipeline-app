# ADR-02: FastAPI Backend + Streamlit Frontend Split

**Status:** Accepted  
**Date:** 2025-05-08

---

## Context

[rag-pipeline-from-scratch](../../rag-pipeline-from-scratch) was a single Python script (`query.py`) — no HTTP boundary, no separation between retrieval logic and presentation. For a portfolio piece, that's fine. For anything that needs to be shared, tested, or extended, it has clear limits:

- No other client can call the RAG pipeline (CLI, mobile, another service)
- No way to test retrieval and generation logic without invoking the UI
- Streamlit's execution model (re-runs the whole script on every interaction) doesn't compose well with expensive startup operations like loading the embedding model or building the BM25 index

## Decision

Split into two independent processes:

1. **FastAPI backend** (`api/`) — owns all AI logic (retrieval, generation, observability). Exposes a versioned REST API with OpenAPI schema. Starts once, holds all expensive state (embedding model, BM25 index, Chroma client) in memory.

2. **Streamlit frontend** (`ui/`) — pure presentation layer. Makes HTTP requests to the API. No AI logic, no database connections.

Communication: HTTP/SSE. The backend streams tokens via Server-Sent Events; the frontend consumes them with `requests` in streaming mode.

## Alternatives Considered

| Option | Pros | Cons | Decision |
|--------|------|------|----------|
| Monolith (everything in Streamlit) | Simpler deploy | Can't test core logic, embedding model restarts on every Streamlit rerun, no API for other clients | Rejected |
| **FastAPI + Streamlit (chosen)** | Testable, reusable API; Streamlit stays thin | Two processes to manage | Accepted |
| FastAPI + Next.js | Production-grade frontend | Overkill for portfolio demo; requires JS build pipeline | Reserved for domain-agent-portfolio |
| FastAPI + Gradio | Easy streaming support | Less control over layout, weaker auth story | Rejected |

## Consequences

**Positive:**
- `core/` and `api/` can be unit tested without a browser.
- Any future client (eval harness, CLI tool, agent) calls the same `/api/v1/query` endpoint — no code duplication.
- The API's OpenAPI schema (auto-generated by FastAPI at `/docs`) is a portfolio artifact — shows you can produce API contracts.
- Dockerizing the split is clean: two containers, one volume for shared Chroma/SQLite state.

**Negative:**
- Two processes to start locally (`uvicorn` + `streamlit`). Mitigated by `make dev` and `make demo` shortcuts.
- SSE streaming across HTTP adds latency vs in-process generator (~5ms per request). Imperceptible in practice.
- Shared `obs.db` and `chroma_db` via volume requires care in a multi-replica deployment. At portfolio scale (1 instance), this is fine.

## API Contract (summary)

```
POST /api/v1/query         → QueryResponse (blocking)
POST /api/v1/query/stream  → text/event-stream (SSE tokens)
POST /api/v1/ingest        → IngestResponse
GET  /api/v1/health        → HealthResponse
GET  /api/v1/queries       → list of recent queries (observability)
```

Full schema available at `http://localhost:8000/docs` when the server is running.
